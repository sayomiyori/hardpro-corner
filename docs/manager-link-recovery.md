# Читатель 1С: работа без доступа к 1С и восстановление после отключения питания

Менеджер отвечает всегда. Каталог берётся из рабочей 1С, а при её недоступности — из
последнего сохранённого снимка. Снимок обновляется сам: каждое удачное чтение 1С
записывает его на диск (`~/.local/share/hardpro/onec-pilot/live-snapshot.json`), поэтому
после отключения света менеджер отвечает по данным последнего рабочего чтения, а не по
устаревшей выгрузке от 18 ноября.

## Слои и их поведение

| Слой | Пока всё работает | При отключении 1С или Hoster |
| --- | --- | --- |
| Qwen3-14B (vLLM) | отвечает за 0,1–0,5 с | не затрагивается: модель локальная |
| `hardpro-catalog` | читает 1С, сохраняет снимок | отвечает по снимку, помечает дату |
| Канал до 1С | SSH к SpaceWeb → Hoster | `hardpro-link-guard.timer` проверяет раз в три минуты и перезапускает канал |
| Читатель 1С на Hoster | держит сеанс COM | сторож `reader_watchdog.ps1` поднимает процесс и туннель |

При недоступной 1С ответ начинается так:

```
Рабочая 1С сейчас не отвечает, отвечаю по последней выгрузке на 24.11.2026 12:05 МСК.
Свежее наличие и брони не подтверждены.
```

Повторные вопросы в течение двух минут не ждут мёртвый канал: `hardpro-catalog` держит
паузу после сбоя. Проверено: первый вопрос после простоя — 10,5 с, следующие — 0,09 с.

## Что поднимается само после перезагрузки Ubuntu

Все пользовательские службы запускаются через linger, без входа в систему:

- `hardpro-vllm` — модель; ждёт монтирования `/srv/models` (`Requires=srv-models.mount`),
  перезапускается без лимита попыток;
- `hardpro-catalog`, `hardpro-onec-link`, `hardpro-openwebui`, `hardpro-gateway`,
  `hardpro-trace`, `hardpro-hub`, `hardpro-agent`, `hardpro-widget`;
- `hardpro-link-guard.timer` — сторож канала к 1С.

Проверка выполнена перезагрузкой сервера: через 30–40 секунд `/health` модели отвечает
200, менеджер отдаёт список вариантов по снимку, Open WebUI открывается. Внешних действий
не потребовалось.

## Что нужно один раз сделать на Hoster

1. BIOS/серверная панель: **Restore AC Power Loss = Power On**, иначе после отключения
   питания сервер останется выключенным до нажатия кнопки.
2. Служба 1С и SQL должны стартовать автоматически — это штатные службы Windows.
3. Зарегистрировать сторожа читателя от SYSTEM (без этого сеанс COM умирает вместе с RDP):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File install_reader_watchdog.ps1
```

Задача `HARD-PRO 1C reader watchdog` запускается при старте системы и каждые две минуты
проверяет порт `18771`, поднимая читатель и обратный SSH-туннель. Журнал — `watchdog.log`
рядом со скриптом.

## Проверка канала и очевидные причины

```bash
systemctl --user status hardpro-onec-link.service --no-pager
journalctl --user -u hardpro-catalog.service -n 40 --no-pager | grep -i 'канал рабочей 1С'
journalctl --user -u hardpro-link-guard.service --no-pager | tail
```

- `RemoteDisconnected` после TLS-рукопожатия — соединение закрыто до HTTP-ответа.
  На Hoster проверьте `watchdog.log`, запуск читателя и открытие сеанса `Retail`.
- `ConnectionRefusedError` — туннель есть, читателя нет: задача на Hoster не запущена.
- `TimeoutError` — сеть или SpaceWeb; проверить `ping 195.208.123.14` и `systemctl --user
  restart hardpro-onec-link`.

Проверка без внешнего инструмента — один вопрос в Open WebUI. Ответ с датой снимка
означает, что слой модели и каталога живы, а 1С недоступна.

Для проверки источника через `onec_work` прочитайте несколько строк номенклатуры
или точный вариант из регистра розничных цен и остатков. Это проверяет базу через MCP.
Фраза «проверь подключение к 1С» в Open WebUI отдельно проверяет маршрут до читателя. Если MCP
читает данные, а чат возвращает ошибку, проверьте задачу `HARD-PRO 1C reader watchdog` на Hoster
и процесс, который слушает порт читателя. При перезапуске завершите только процесс
`onec_reader_windows.py` и используйте существующую задачу Планировщика для его запуска.
