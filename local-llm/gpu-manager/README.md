# Менеджер трёх GPU для Flash Next

Менеджер переключает рабочую раскладку (14B на GPU 0, 27B на GPU 1, ComfyUI на GPU 2) и Qwen3.8 Flash Next на всех трёх картах. Для NCCL он освобождает карты, передаёт их через VFIO гостю Linux и запускает там один процесс llama.cpp. После остановки VM он проверяет возврат тех же карт по UUID, поднимает выбранные службы и возвращает исходные привязки ролей каталога.

| Контекст | Токенов | Микробатч |
| --- | ---: | ---: |
| 16K | 16 384 | 2 048 |
| 64K | 65 536 | 1 536 |
| 128K | 131 072 | 256 |

Во всех трёх рецептах используются тензорное разбиение `1,1,1`, NCCL AllReduce, PCIe P2P, KV-кеш F16 и один параллельный запрос. При загрузке гостя `vm/all-pairs` проверяет шесть направлений средствами `owner_verify`. Готовность модели требует ответа на четыре токена, более 12 000 МиБ у одного PID на каждой карте и прямых каналов NCCL с участием всех трёх GPU в журнале текущего запуска. [Условия и результаты исходного стенда](../../docs/three-3090-flash-next.md).

## Подготовка своего стенда

1. На хосте нужны Linux с systemd, Python 3.10+ с pidfd, NVIDIA CLI, QEMU/KVM, OVMF, VFIO, отдельная группа IOMMU для каждой пары GPU + аудиофункция и настроенный [каталог моделей](../../hardpro-hub/bin/hp-model.py). Рабочие службы 14B и ComfyUI должны быть пользовательскими юнитами systemd. Зарегистрируйте 27B как `llamacpp` на GPU 1. Для выбора обычных профилей Flash без NCCL отдельно зарегистрируйте их в каталоге хоста.
2. Скопируйте этот каталог в `~/.local/share/gpu-manager` владельца служб. В `~/.config/gpu-manager/settings.json` положите заполненную копию `settings.example.json`, а в `~/.config/gpu-manager/vm.conf` — копию `vm/vm.conf.example`. Подставьте PCI-адреса в порядке индексов NVIDIA, имена служб и моделей, порты и пути к весам. Для разрешённого фонового процесса дисплея задайте одновременно `display_executable` и `display_unit`; системные службы, освобождающие устройства, перечислите в `display_units`. Настраивайте эти значения при остановленной VM. Каталог VM с образами, сокетом монитора и файлами состояния должен принадлежать владельцу служб и иметь права 0700.
3. В каталоге `vm/` подготовьте системный QCOW2, отдельную копию переменных OVMF `vars.fd`, `seed.img` и том SquashFS `weights.sqfs` с GGUF и совместимой сборкой llama.cpp с NCCL. Гость монтирует том в `/srv/gpu-weights`. В домашнем каталоге гостевого пользователя нужен исполняемый [owner_verify](../../docs/three-3090-flash-next.md), а в `~/.local/share/gpu-manager/` — файлы `guest-model.py` и `settings.py`. В гостевой `~/.config/gpu-manager/settings.json` нужны только `nccl_ports`, `guest_model_path` и `guest_binary`. Порты должны совпадать с хостом. У гостя должны работать CUDA P2P, пользовательский systemd и чтение журналов своих юнитов.
4. Настройте на хосте SSH-псевдоним `gpu-manager-guest` на loopback и порт `ssh_port`, с проверенным ключом хоста гостевой VM. QEMU ограничивает гостевую сеть и публикует порты SSH и моделей только на loopback. Скрипты ожидают настроенный администратором доступ к VFIO, управлению питанием и указанным системным службам. В госте нужны права для монтирования тома и штатного выключения. После подготовки образа создайте маркер `image-ready` в каталоге VM.
5. Установите юнит и зарегистрируйте рецепты от имени пользователя служб.

```sh
cd ~/.local/share/gpu-manager
install -Dm644 vm/gpu-manager-vm.service ~/.config/systemd/user/gpu-manager-vm.service
systemctl --user daemon-reload
python3 register-profiles.py
```

## Переключение и проверка

Исполнитель `gpu_profiles.py request` читает один объект JSON из stdin. Запрос `plan` проверяет очереди, владельцев GPU и настройки каталога. Для `apply` требуются подпись этого плана и UUID операции. Повтор запроса с тем же UUID возвращает состояние существующего задания. Пример для оболочки Bash с jq:

```sh
cd ~/.local/share/gpu-manager
request='{"mode":"plan","layout":["flash","flash","flash"],"flash":"Qwen3.8-Flash-Next-64K-3GPU-NCCL"}'
plan=$(python3 gpu_profiles.py request <<< "$request") || exit 1
jq . <<< "$plan"
# После просмотра плана
jq --arg sig "$(jq -er .signature <<< "$plan")" --arg id "$(python3 -c 'import uuid; print(uuid.uuid4())')" \
  '. + {mode:"apply",signature:$sig,id:$id}' <<< "$request" | python3 gpu_profiles.py request
echo '{"mode":"status"}' | python3 gpu_profiles.py request
python3 monitor.py
```

Дождитесь `done`. Для возврата повторите планирование и применение с `{"mode":"plan","layout":["manager","coder","comfy"]}`. Если очередь занята или состав процессов изменился, менеджер отклонит запрос. При частичном переключении он попытается восстановить прежнюю раскладку. Статус `needs_recovery` означает, что восстановление требует проверки оператором.

## Подключение к панели

Разместите `panel.html` и `profile-ui.js` в панели администратора. Для чтения нужны `GET /api/session` (поле `token`) и `GET /api/profile-status`. Для переключения нужен `POST /api/profile`. Подключите функцию `remote` из `profile_api.py` к этим обработчикам после серверной проверки полномочий, а для POST также проверяйте origin и CSRF-токен из заголовка `X-Control-Token`. Для статуса передавайте `{"mode":"status"}`. Первым аргументом `remote` получает фиксированный список аргументов команды `python3 /путь/gpu_profiles.py request` на хосте исполнителя. Клиент передаёт только JSON. Панель позволяет выбрать контекст, посмотреть план, подтвердить переключение и следить за заданием.

## Автономные проверки

```sh
python3 -m unittest discover -s . -v
for f in vm/{all-pairs,attach,boot-vm,config,control,guest,launch,release-vm,restore}; do bash -n "$f" || exit 1; done
node --check profile-ui.js
```

Тесты используют вымышленные настройки и подменяют обращения к GPU. Они проверяют аргументы запуска каждого контекста, регистрацию профилей, отказ при отсутствии прямых каналов, защиту от устаревшего плана и восстановление раскладки. Физические замеры исходной реализации приведены в отчёте по ссылке выше.
