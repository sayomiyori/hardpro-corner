# Ускорение 27B (Huihui-Qwen3.8-27B-abliterated-Q5_K) на hard-pro-llm

Комплект для измеряемого разгона llama.cpp-сервера 27B: повторяемый набор
запросов, скрипты включения speculative decoding и отката, агрегатор результатов.

## Модель и точка входа

- Файл: `/srv/models/weights/coding/Huihui-Qwen3.8-27B-abliterated-Q5_K.gguf` (19,5 ГБ),
  архитектура GGUF `qwen35`, гибрид: gated-delta-слои + полный attention каждый 4-й слой
  (`full_attention_interval = 4`), 4 KV-головы по 256 dim.
- В весах есть MTP-голова: `qwen35.nextn_predict_layers = 1`, тензоры `blk.64.nextn.*`.
  Проверено чтением метаданных GGUF — вторую копию модели для этого не грузили.
- Сборка llama.cpp: `b12375` / commit `9d25e0014` (`llama serve`, единый бинарник).
- Сервис: `hardpro-abliterated-27b`, порт 8084, каталог моделей `~/hardpro/models/profiles.json`,
  роль одна карта — одна модель (GPU 1, `CUDA_VISIBLE_DEVICES` от переключателя).

## Что даёт выигрыш

Три рычага проверены измерениями (одинаковый набор, sampling зафиксирован):

1. **MTP speculative decoding** (`--spec-type draft-mtp --spec-draft-n-max 2`) —
   черновые токены генерирует MTP-голова из самих весов, дополнительно ничего
   не скачивается. Декод ускоряется в ~1.5–1.8×, prefill и TTFT не меняются.
2. **Flash Attention + KV q8_0/q8_0** — уже работали в baseline через явные флаги;
   повторного выигрыша от них ждать не стоит, включать для сверки смысла нет.
3. **Prefix cache** — при повторных запросах с общим началом TTFT падает
   с ~30 с до ~0,2 с; работает и между разными промптами с общим префиксом.

### Замеры 21.11.2026 (медианы, GPU RTX 3090, threads 16, parallel 1, контекст 65536)

| случай | вход | baseline decode | mtp1 (n=1) | mtp2 (n=2) |
| --- | --- | --- | --- | --- |
| short_code (256 out) | ~223 | 38,5 т/с | ~55 т/с | ~70 т/с |
| short_tool (tool calls) | ~390 | 38,3 т/с | ~59 т/с | ~71 т/с |
| long32, fresh | 33 274 | 32,3 т/с | ~52 т/с | ~56 т/с |
| long60, fresh | 62 103 | 28,4 т/с | ~45 т/с | ~49 т/с |

TTFT (prefill ~1150 т/с на 33K, ~870–905 т/с на 62K): 28,5–33,9 с на свежем вводе,
0,13–0,26 с при повторном префиксе. Пиковая VRAM: 20,6 ГиБ baseline,
21,6 ГиБ с MTP n=2 (запас ~2,9 ГиБ на карте 24 ГиБ).

Счётчики MTP из журнала сервера (короткая кодовая задача):
`draft acceptance = 0.66 (113 accepted / 171 generated), mean len = 2.31`.

Ограничения честно: `n_max = 3` не проверен; влияние `--ubatch-size` на prefill
не проверен; ngram-спекуляция для задач правки кода не проверена. Длинные случаи
сравнивались по 2 прогона на конфигурацию, один из них завершился по EOS.

## Как воспроизвести

```bash
# 0) убедиться, что сервер простаивает
curl -s http://127.0.0.1:8084/slots

# 1) baseline (текущий запуск)
bash run_suite.sh baseline

# 2) кандидат: MTP, черновик до 2 токенов (рестарт только 27B штатным hp-model)
bash exp_mtp.sh draft-mtp 2
bash run_suite.sh mtp2

# 3) сводка по всем тегам
python3 aggr.py

# откат к предыдущему профилю каталога и рестарт 27B
bash rollback.sh
```

`exp_mtp.sh` перезаписывает `args` профиля `hardpro-abliterated-27b` в
`profiles.json` (n_ctx 65536 + spec-флаги), делает копию профиля рядом и
перезапускает сервис через штатный переключатель (`hp-model stop` + `launch`).
Держать порт, alias, шаблон, reasoning-режим и KV-типы неизменными — их меняет
только правка профиля, поэтому сравнение остаётся корректным.

## Граница применимости

- Флаги `--spec-type draft-mtp` существуют в этой сборке; для другой версии
  llama.cpp сверь `llama serve --help` — синтаксис спекулятивного декода менялся.
- MTP работает только когда в GGUF есть `nextn`-тензоры: имя файла не доказательство,
  проверяй метаданные (см. [gguf_dump](https://github.com/ggml-org/llama.cpp/blob/master/gguf-py/gguf/scripts/gguf_dump.py)).
- Замеры зависят от скважности запросов к другим сервисам; перед сравнением
  убедись, что 14B-менеджер на GPU 0 и остальные службы в том же режиме.
